## k6 version

k6.exe v2.2.0 (commit/00a9a1b7f5, go1.26.5, windows/amd64)

# 1. Чанарын сценарио

## 1.1 Performance сценарио — `/cart/add`

| Хэсэг                  | Тайлбар                                                                          |
| ---------------------- | -------------------------------------------------------------------------------- |
| **Тойм**               | Хэрэглэгч сагсанд бараа нэмэх үед API хурдан хариу өгөх шаардлагатай.            |
| **Системийн төлөв**    | Express сервер хэвийн ажиллаж байгаа бөгөөд `/cart/add` endpoint идэвхтэй байна. |
| **Орчны төлөв**        | Локал сервер дээр хэвийн ачаалалтай, 20 VU зэрэг ажиллана.                       |
| **Гадаад өдөөлт**      | 20 виртуал хэрэглэгч 1 минутын турш `/cart/add` endpoint рүү хүсэлт илгээнэ.     |
| **Шаардлагатай хариу** | Хүсэлтүүд амжилттай боловсруулагдаж, хариу богино хугацаанд буцна.               |
| **Хэмжүүр**            | `/cart/add` endpoint-ийн response time-ийн p95 нь 200 ms-ээс бага байна.         |

### SLO

| Сценарио    | SLI                 | Босго            | Цонх / нөхцөл  |
| ----------- | ------------------- | ---------------- | -------------- |
| Performance | `/cart/add` latency | **p95 < 200 ms** | 20 VU, 1 минут |

**Босго сонгосон үндэслэл:** `/cart/add` нь сервер дээр нэмэлт хүлээлтгүйгээр шууд JSON response буцаадаг бөгөөд response time нь хэвийн үед ойролцоогоор 1–5 ms байдаг. Тиймээс 200 ms-ийн p95 босго нь хэвийн ачааллын үед биелэх бодитой шаардлага юм.

## 1.3 Availability сценарио — Сервер crash/restart (Chaos туршилт)

| Хэсэг                  | Тайлбар                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| **Тойм**               | Сервер гэнэт зогссон үед дахин асах хүртэлх хугацаанд үйлчилгээ хэрхэн нөлөөлөхийг шалгана. |
| **Системийн төлөв**    | Express сервер ажиллаж, гурван endpoint үйлчилгээ үзүүлж байна.                             |
| **Орчны төлөв**        | 20 VU сервер рүү тогтмол хүсэлт илгээнэ.                                                   |
| **Гадаад өдөөлт**      | k6 тест ажиллаж байх үед серверийг Ctrl+C-ээр зогсоож, 10 секундийн дараа дахин асаана.     |
| **Шаардлагатай хариу** | Сервер дахин ассны дараа хүсэлтүүд дахин амжилттай боловсруулагдана.                        |
| **Хэмжүүр**            | Нийт хүсэлтийн амжилтын хувь ≥ 90%, серверийн сэргэх хугацаа 10 секунд байна.        |

### SLO

| Сценарио     | SLI                         | Босго     | Цонх / нөхцөл                 |
| ------------ | --------------------------- | --------- | ----------------------------- |
| Availability | Нийт хүсэлтийн амжилтын хувь (`checks`) | **≥ 90%** |  1–2 минут, 10 сек зогсолт    |

**Босго сонгосон үндэслэл:** Серверийг 10 секунд зориудаар зогсоох тул нийт хүсэлтийн амжилтын хувь 90%-иас багагүй байхаар SLO босгыг сонгосон.

### Error budget

2 минут = 120 секунд.

Availability SLO:

**90%**

Тэгэхээр зөвшөөрөгдөх downtime:

**120 × (1 - 0.90) = 12 секунд**

Иймээс энэ SLO-ийн хугацааны error budget нь **12 секунд** байна.

### Хүсэлтээр тооцсон Error Budget ба зөрүүний тайлбар

k6-ийн `checks` metric нь хугацааны хувь биш, **хүсэлтийн тооны хувь** юм. Сервер хэвийн ажиллаж байх үед `/report` endpoint 200–400 ms орчим хүлээдэг бол сервер зогссон үед хүсэлтүүд `connection refused` хэлбэрээр маш хурдан амжилтгүй болдог.

Иймээс сервер зогссон 10 секундэд хэвийн үеийнхээс олон хүсэлт амжилтгүй болж, хүсэлтээр тооцсон availability хурдан буурдаг. Манай туршилтаар availability **86.89%** болсон бөгөөд энэ нь цагаар тооцсон 12 секундийн error budget-тэй шууд адил утгатай биш юм — цагаар бол 10/120=8.3% downtime, харин хүсэлтээр 13.11% алдаа гарсан нь сервер унасан секунд бүрт хэвийн секундээс хавьгүй олон хүсэлт "амжилтгүй болж"-тэй холбоотой.

# 2. SLO → k6 threshold

Дээрх SLO-уудыг k6 threshold болгон дараах байдлаар кодчилсон.

| Сценарио | k6 metric | Threshold |
|---|---|---|
| **Performance** | `http_req_duration{name:cart}` | `p(95)<200` |
| **Reliability** | `http_req_failed{name:pay}` | `rate<0.08` |
| **Availability** | `checks` | `rate>0.90` |
| **Нэмэлт Performance** | `http_req_duration{name:report}` | `p(95)<450` |

Threshold-ийн утгууд нь дээр тодорхойлсон SLO-той ижил байна. Ингэснээр чанарын шаардлагыг k6 тестээр автоматаар шалгах боломжтой болсон.

# 3. Туршилтын үр дүн

Туршилтын үр дүнг `results/` хавтас дахь файлуудаар хадгалсан.

## 3.1 PASS туршилтын үр дүн — `results/pass.txt`

Сервер хэвийн ажиллаж байх үеийн үр дүн:

| Metric                                 |        Үр дүн | Төлөв |
| -------------------------------------- | ------------: | ----- |
| `checks`                               |      **98.41%** | PASS  |
| `http_req_duration{name:cart}` p(95)   |   **3.56 ms** | PASS  |
| `http_req_duration{name:report}` p(95) | **398.14 ms** | PASS  |
| `http_req_failed{name:pay}` rate       |     **4.75%** | PASS  |

Үр дүнгээс харахад сервер хэвийн ажиллаж байх үед бүх тодорхойлсон threshold биелсэн.

## 3.2 Chaos туршилтын үр дүн — `results/chaos.txt`

Тест ажиллаж байх үед серверийг **10 секунд зогсоож**, дараа нь дахин асаасан.

| Metric                                    |     Үр дүн | Төлөв |
| ----------------------------------------- | ---------: | ----- |
| `checks` (Availability)                   | **86.89%** | FAIL  |
| `http_req_failed{name:pay}` (Reliability) | **16.37%** | FAIL  |

Сервер зогссон хугацаанд `connection refused` алдаанууд бодитоор гарсан (0m13с-аас 0m23с орчимд, ~10 секундын турш). Сервер унах үед бүх endpoint түр хугацаанд ажиллахгүй болсон тул нэг crash нь Availability болон Reliability SLO-г хоёуланг нь нэгэн зэрэг FAIL болгосон.

Энэ туршилтаас харахад Availability болон Reliability хэмжүүрүүдийг тусад нь авч үзэх шаардлагатай байна. Ялангуяа сервер бүхэлдээ унтарсан үед `/pay` endpoint-ийн reliability-г зөвхөн сервер ажиллаж байсан үеийн хүсэлтүүдээр тусад нь хэмжих нь илүү тохиромжтой байж болно.

## 3.3 Зориуд FAIL болгосон туршилтын үр дүн — `results/fail.txt`

`slo-test-fail.js` файлд `/report` endpoint-ийн threshold-ийг зориудаар:

```text
p(95)<100
```

болгож өөрчилсөн.

Туршилтаар:

```text
http_req_duration{name:report}
p(95) = 396.69 ms
```

гэсэн үр дүн гарсан.

396.69 ms нь 100 ms-ийн босгоос их тул threshold зөрчигдөж, тест **FAIL** болсон.

k6-ийн гаралт дээр:

```text
time="..." level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
```

гэсэн мэдээлэл гарсан.

Мөн PowerShell дээр:

```text
exit=99
```

гэсэн exit code гарсан.

Энэ нь threshold зөрчигдсөн үед k6 нь `0`-ээс ялгаатай exit code буцааж чаддагийг харуулж байна. Иймээс CI/CD pipeline-д threshold-ийн зөрчлийг автоматаар илрүүлж, pipeline-ийг зогсоох боломжтой.

# 4. Дүгнэлт

Энэ лабораторийн ажлаар чанарын сценариог SLO болгон тодорхойлж, тэдгээрийг k6 threshold хэлбэрээр автоматжуулах бүтэн дарааллыг практикт хэрэгжүүлж сурлаа.

Performance сценариод /cart/add endpoint-ийн response time-ийн p95-ийг 200 ms-ээс бага байхаар тодорхойлж, туршилтаар 3.56 ms гэсэн үр дүн гарсан. Reliability сценариод /pay endpoint-ийн error rate-ийг 8%-иас бага байхаар тодорхойлж, хэвийн туршилтаар 4.75% гэсэн үр дүн гарсан.

Chaos туршилтын үед серверийг 10 секунд зориудаар зогсооход connection refused алдаанууд бодитоор гарч, availability 86.89% болж SLO босгоос доош орсон. Энэ туршилтаар серверийн crash нь Availability болон Reliability хэмжүүрүүдэд нэгэн зэрэг нөлөөлж болохыг ажигласан.

Мөн цагаар тооцсон error budget болон k6-ийн хүсэлтийн тоогоор тооцсон availability нь ижил ойлголт биш болохыг туршилтаар харуулсан. Сервер зогссон үед хүсэлтүүд маш хурдан connection refused болж дуусдаг тул богино хугацаанд олон хүсэлт амжилтгүй болж, хүсэлтээр тооцсон availability хурдан буурдаг.

Зориуд threshold эвдэх туршилтаар /report endpoint-ийн p95 нь 396.69 ms болж, зориуд тавьсан p(95)<100 босгыг зөрчсөн. Үүний үр дүнд k6 exit code 99 буцаасан нь threshold-ийг CI/CD pipeline-д чанарын автомат шалгуур болгон ашиглах боломжтойг харуулсан.

Ингэснээр системийн чанарыг зөвхөн хэвийн ажиллагааны үед бус, ачаалал болон эвдрэлийн нөхцөлд мөн хэмжиж, тодорхой SLO-г автомат threshold-ээр шалгах үндсэн ойлголтыг практикт хэрэгжүүллээ.
