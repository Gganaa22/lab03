**Оюутны нэр:** Д.Гантогтох

## k6 version

k6.exe v2.2.0 (commit/00a9a1b7f5, go1.26.5, windows/amd64)

# 1. Чанарын сценарио

| ---------------------- | -------------------------------------------------------------------------------- |

| **Гадаад өдөөлт**      | 20 виртуал хэрэглэгч 1 минутын турш `/cart/add` endpoint рүү хүсэлт илгээнэ.     |

## 1.3 Availability сценарио — сервер crash/restart

| Хэсэг                  | Тайлбар                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| **Тойм**               | Сервер гэнэт зогссон үед дахин асах хүртэлх хугацаанд үйлчилгээ хэрхэн нөлөөлөхийг шалгана. |
| **Системийн төлөв**    | Express сервер ажиллаж, гурван endpoint үйлчилгээ үзүүлж байна.                             |
| **Орчны төлөв**        | 10 VU сервер рүү тогтмол хүсэлт илгээнэ.                                                    |
| **Гадаад өдөөлт**      | k6 тест ажиллаж байх үед серверийг Ctrl+C-ээр зогсоож, 10 секундийн дараа дахин асаана.     |
| **Шаардлагатай хариу** | Сервер дахин ассны дараа хүсэлтүүд дахин амжилттай боловсруулагдана.                        |
| **Хэмжүүр**            | Бүх хүсэлтийн амжилтын хувь ≥ 90%, мөн серверийн сэргэлтийн хугацаа 10 секунд байна.        |

### SLO

| Сценарио     | SLI                         | Босго     | Цонх / нөхцөл                 |
| ------------ | --------------------------- | --------- | ----------------------------- |
| Availability | Бүх хүсэлтийн амжилтын хувь | **≥ 90%** | 2 минут, 10 секундийн зогсолт |

**Босго сонгосон үндэслэл:** 2 минутын тестийн үед серверийг 10 секунд зориудаар зогсоох тул нийт үйлчилгээний амжилтын хувь 90%-иас багагүй байх босго сонгосон.

### Error budget

2 минут = 120 секунд.

Availability SLO:

**90%**

Тэгэхээр зөвшөөрөгдөх downtime:

**120 × (1 - 0.90) = 12 секунд**

Иймээс энэ SLO-ийн хугацааны error budget нь **12 секунд** байна.

# 2. SLO → k6 threshold

Дээрх SLO-уудыг k6 threshold болгон дараах байдлаар кодчилно.

| Сценарио           | k6 metric                      | Threshold   |
| ------------------ | ------------------------------ | ----------- |
| Performance        | `http_req_duration{name:cart}` | `p(95)<200` |
| Reliability        | `http_req_failed{name:pay}`    | `rate<0.08` |
| Availability       | `checks`                       | `rate>0.90` |
| Нэмэлт Performance | `/report` latency              | `p(95)<450` |

`/report` endpoint нь 200–400 ms орчим хүлээлттэй тул нэмэлт дөрөв дэх threshold болгон `p(95)<450` босгыг ашиглана.

---

# 3. Error budget-ийн тайлбар

Availability SLO нь 2 минутын цонхонд 90% байгаа тул хугацаагаар тооцсон error budget нь 12 секунд байна.

Гэхдээ k6-ийн `checks` metric нь хугацааны хувь биш, **амжилттай хүсэлтийн нийт хүсэлтэд эзлэх хувь** юм. Сервер зогссон үед хүсэлтүүд хурдан хугацаанд connection error-оор буцаж болох тул 10 секундийн downtime нь заавал яг 10 секундийн хэмжээний хүсэлтийн алдаа гэсэн үг биш.

Иймээс хугацаагаар тооцсон 12 секундийн error budget болон хүсэлтээр тооцсон availability-ийн үр дүн хоорондоо ялгаатай байж болно.

---

# 4. Дүгнэлт

Энэ лабораторийн ажлаар чанарын сценариог SLO болгон тодорхойлж, дараа нь k6 threshold хэлбэрээр автомат шалгалтад оруулах дарааллыг хэрэгжүүлсэн. Performance сценариод `/cart/add` endpoint-ийн хариу өгөх хугацааг p95 хэмжүүрээр тодорхойлсон. Reliability сценариод `/pay` endpoint-ийн алдааны давтамжийг error rate-аар хэмжсэн. Availability сценариод серверийг зориудаар зогсоож, дахин ажиллуулснаар үйлчилгээний хүртээмжийг шалгасан. SLO-ийн босго сонгохдоо серверийн endpoint-үүдийн бодит зан төлөвийг харгалзан үзсэн. Availability-ийн хувьд 2 минутын цонхонд 90%-ийн SLO нь 12 секундын хугацааны error budget үүсгэж байгааг тооцсон. Мөн k6-ийн checks нь хугацаагаар биш хүсэлтийн тоогоор availability-г хэмждэг тул хоёр төрлийн error budget өөр байж болохыг ойлгосон. Threshold-уудыг k6 script-д metric болон endpoint-ийн tag ашиглан тусгаарласан. Нэмэлтээр `/report` endpoint-д latency-ийн threshold нэмснээр дөрөв дэх шалгалтыг хийсэн. Ийнхүү чанарын сценарио → SLO → threshold гэсэн дарааллыг практик туршилтаар хэрэгжүүлсэн.
